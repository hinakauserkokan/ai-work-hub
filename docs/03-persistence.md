# Persistence

## What we built

The dashboard, projects, and task-board pages used to keep their data in a `List<T>` inside
each page's `@code` block, so a browser refresh reset everything. This milestone replaces
that with a real PostgreSQL database, read and written through Entity Framework Core (EF Core).

```text
Razor page  →  Service (ProjectService / WorkItemService)  →  AiWorkHubDbContext  →  PostgreSQL
```

- **Models** (`Models/`): `Project`, `WorkItem`, and `TeamMember` are plain C# classes describing
  the shape of the data. `WorkItem` (not `Task`) avoids clashing with `System.Threading.Tasks.Task`.
  `ProjectStatus`, `WorkItemStatus`, and `WorkItemPriority` are enums stored as text in the
  database, so a row is still readable if you inspect the table directly.
- **`Data/AiWorkHubDbContext.cs`**: the EF Core "gateway" to the database. It exposes a
  `DbSet<T>` per table and configures relationships in `OnModelCreating` — for example, a
  project can have many team members and a team member can be on many projects, and EF Core
  creates the join table for that automatically (no hand-written join entity needed).
- **`Data/Migrations/`**: generated by `dotnet ef migrations add`. A migration is a versioned,
  reviewable description of a schema change; `dotnet ef database update` (or `Database.Migrate()`
  at startup, which `Program.cs` now calls automatically) applies any migrations the database
  hasn't seen yet.
- **`Data/DbSeeder.cs`**: inserts the same sample projects, team members, and tasks the pages
  used to hardcode, so the app looks the same the first time you run it against an empty database.
- **Services** (`Services/ProjectService.cs`, `Services/WorkItemService.cs`): the only classes
  that talk to `AiWorkHubDbContext`. Pages call these instead of touching EF Core directly, which
  keeps data-access logic in one place per entity.

## Files to read, in order

1. `Models/Project.cs`, `Models/WorkItem.cs`, `Models/TeamMember.cs` — the domain shapes.
2. `Data/AiWorkHubDbContext.cs` — how those shapes become database tables and relationships.
3. `Data/Migrations/` — the generated schema history (open the newest `*_InitialCreate.cs`).
4. `Data/DbSeeder.cs` — the sample data loaded into a fresh database.
5. `Services/ProjectService.cs` and `Services/WorkItemService.cs` — CRUD methods the pages call,
   returning `ProjectSummary` / `WorkItemSummary` records shaped for what the markup needs.
6. `Components/Pages/Projects.razor`, `MyTasks.razor`, `Home.razor` — now inject a service and
   load data in `OnInitializedAsync` instead of declaring it in `@code`.

## EF Core terms introduced

| Term | Meaning in this project |
| --- | --- |
| `DbContext` | The class that represents a connection to the database and tracks entity changes (`AiWorkHubDbContext`). |
| `DbSet<T>` | A queryable, updatable collection mapped to one database table, e.g. `db.Projects`. |
| Migration | A generated, versioned file describing one schema change, created by `dotnet ef migrations add <Name>`. |
| Fluent configuration | The `OnModelCreating` code that describes relationships, max lengths, and enum conversions in C#, instead of attributes. |
| Skip navigation | A many-to-many relationship (`Project.Members` ↔ `TeamMember.Projects`) where EF Core manages the join table for you. |
| Seeding | Inserting starter rows — here, done in code (`DbSeeder`) rather than baked into a migration, so it's easy to change without a new migration. |

## Local database setup

The app expects a PostgreSQL server reachable with the connection string in
`appsettings.Development.json` (defaults to a local `aiworkhub_dev` database, no password,
matching a local trust-authenticated Postgres install). To set one up from scratch:

```bash
createdb aiworkhub_dev
dotnet tool restore
dotnet ef database update --project src/AiWorkHub
```

`dotnet run` also calls `Database.Migrate()` on startup, so once the database exists, pending
migrations are applied automatically — the explicit `dotnet ef database update` command above is
mainly useful when you want to apply a migration without starting the app, or when you add a new
migration later (`dotnet ef migrations add <Name> --project src/AiWorkHub --output-dir Data/Migrations`).

## What's still temporary

- There's no per-user filtering yet — "My tasks" shows every task in the workspace, because
  there's no signed-in user. That arrives with the Accounts/Auth milestone.
- Comments and activity history are still absent; the dashboard's "Recent activity" panel and
  the AI workspace card remain static placeholders until the Collaboration and AI-assistant
  milestones add real data behind them.
